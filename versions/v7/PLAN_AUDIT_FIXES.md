# План устранения проблем по результатам аудита (2026-06-12)

Статус: утверждён пользователем — устраняются ВСЕ пункты аудита.
Источник: пятисторонний аудит (MCTS, тренировочный пайплайн, генерация данных/солверы,
архитектура сети, эвалюация/производительность). Каждый пункт ниже содержит:
проблему, файлы, конкретный фикс, способ верификации.

ВАЖНО — глобальные следствия:
- Фиксы групп A (архитектура) и B (данные/солвер) меняют семантику модели и
  таргетов → **все существующие чекпоинты и датасеты инвалидируются**. Полный
  ретрейн с фазы 1 после регенерации данных. Делать все фиксы ДО большого запуска.

  невозможно проверить эффект остальных фиксов.

## Этап 0. Метрика: движок + эвалюация (без этого нельзя верить ни одному BB/100)

### 0.1 CRITICAL — Шоудаун уничтожает пот в движке
**Файлы:** `env/table.py:101-108`, `env/table.py:52`
**Проблема:** `next_turn` обнуляет `self.bets` на каждой смене улицы; на шоудауне
`Judger.get_reward` получает только river-ставки (при олл-ине до ривера — нули).
Фишки прошлых улиц лежат в `self.pot` и никому не выплачиваются. Подтверждено
тестом: HU олл-ин 500/500 → оба игрока заканчивают с 0.
**Фикс:**
1. Добавить в `Table` массив `self.cumulative_bets` (накапливается в `step()`,
   НЕ обнуляется в `next_turn`; `step()` уже возвращает ставку 4-м значением —
   тот же источник, что использует `collect.py`).
2. На шоудауне передавать в `Judger.get_reward` `self.cumulative_bets` вместо
   `self.bets`. `Judger.share_out` корректен для side/split-потов (проверено
   аудитом на 4000 матчапов + edge cases) — при подаче полных вкладов сайд-поты
   считаются правильно автоматически.
3. Кредитование: `credits[i] += rewards[i]` (rewards от полных вкладов уже
   включают возврат), убрать прибавку `+ self.bets[i]`, выверить сохранение фишек.
4. Путь fold-win (`table.py:90-92`) не трогать — он корректен.
**Верификация:** тест сохранения фишек: для случайных раздач (включая
мульти-стрит шоудауны, олл-ин ранауты, сайд-поты, сплиты)
`sum(credits_after) == sum(credits_before)` и победитель получает пот.

### 0.2 CRITICAL — Удалить equal-split «коррекцию утечки» в эвалюации
**Файл:** `evaluation/evaluate.py:663-675`
**Проблема:** `leak = -sum(raw_deltas); corrected = raw + leak/num_players` —
делит украденный у победителя пот поровну на всех (HU олл-ин 1000 → дельты (0,0)
независимо от победителя). Метрика слепа к олл-инам и наказывает шоудаун-скилл.
**Фикс:** после 0.1 убрать коррекцию полностью; добавить assert на
консервацию фишек за руку (леак == 0) как страховку от регрессий движка.

### 0.3 MAJOR — Эвалюация измеряет не ту политику
**Файлы:** `evaluation/evaluate.py:196-198, 223, 608`
**Проблема:** dir-based загрузчик жёстко ставит `use_mcts=False`; фаза 6

**Фикс:**

**Верификация:** прогон одного агента в обоих режимах, лог явно печатает policy type.

### 0.5 MAJOR — Opponent-embedding в эвалюации: трёхслойная контаминация
**Файлы:** `evaluation/evaluate.py:121-123, 468, 524, 691`, `perception.py:398-413`
**Проблема:** (1) эмбеддинги ключуются по синтетическим pool-id, а агенты
ротируются по местам → один id усредняет все политики (тренировка ключует по
имени агента — `collect.py:722`); (2) одна `OpponentEmbeddingTable` шарится
всеми 16 столами, батч держит только последний event на opp_id на весь батч →
столы клобберят друг друга; (3) состояние не сбрасывается между матчапами.
**Фикс:**
1. Ключевать эмбеддинги по **имени агента** (консистентно с тренировкой).
2. Отдельная таблица (или составной ключ `(table_id, agent_name)`) на стол.
3. Явный reset таблиц на границе матчапа/ротации пула.
**Верификация:** тест: два стола с одним агентом → их эмбеддинги независимы;
лог идентичности ключей.

## Этап A. Архитектура сети (инвалидирует все чекпоинты)

### A.1 CRITICAL — Модель не каузальная
**Файлы:** `agent/perception/encoder.py:45-47`, `decoder.py:44-46`,
`value/value.py:45-47`, `action/action.py:45-47`,
`opponent_action/opponent_action.py:47-49`
**Проблема:** рукодельная 4D padding-маска передаётся в `Qwen3DecoderLayer`;
в transformers явная маска **отключает** `is_causal` в SDPA → всё внимание
двунаправленное (доказано эмпирически: возмущение последнего токена меняет
позицию 0). Recon-таргет modelling-фазы (`modelling_predict/train.py:116`)
строится на ложной посылке каузальности → утечка будущего в эмбеддинги,
которыми MCTS расширяет контекст.
**Решение:** модель ДОЛЖНА быть каузальной (это посылка modelling/recon и
докстрингов). Фикс во всех пяти модулях:
```python
# вместо padding-only маски строить combined causal + padding:
causal = torch.triu(torch.full((S, S), torch.finfo(dtype).min, device=dev), diagonal=1)
attn_mask = causal[None, None] + (1.0 - mask[:, None, None, :]) * torch.finfo(dtype).min
```
(одна общая util-функция, использовать во всех модулях; следить за dtype под AMP).
**Верификация:** регрессионный тест на каждый модуль: возмущение токена t не
меняет выходы позиций < t (при mask=ones и при реальном паддинге). Тест
закоммитить — это защита от молчаливого возврата бага при апгрейде transformers.

### A.2 CRITICAL — ModellingHead: каузальный self-attn по порядку действий + RoPE вопреки дизайну
**Файлы:** `agent/modelling/modelling.py:153-154` (self-attn без маски →
is_causal=True по индексам fold..allin), `modelling.py:137-142, 151-152`
(RoPE на queries/keys кросс-внимания при докстринге «No RoPE — orderless»).
**Фикс:**
1. В self-attn передавать явную all-visible маску (нули) → запросы действий
   видят друг друга симметрично.
2. Убрать применение RoPE к action-queries и context-keys в кросс-внимании —
   привести код к задокументированному дизайну (позиционная информация уже
   содержится в decoder output).
**Верификация:** тест симметрии: возмущение query действия 13 меняет эмбеддинг
действия 0 (и наоборот) сопоставимо.

### A.3 CRITICAL — `head_dim` молча = 128 (дефолт Qwen3), а не `d_model/n_heads`
**Файлы:** все шесть конструкторов `Qwen3Config`: `encoder.py:17-24`,

**Верификация:** `q_proj.weight.shape == (d_model, d_model)`; пересчёт

## Этап B. Данные и солвер (инвалидирует все датасеты)

### B.1 CRITICAL — Солвер: вэлью-бет никогда не выигрывает при колле
**Файлы:** `agent/gto_utils/gpu_solver_v3.py:616-618, 849`; та же модель в
`gpu_solver_v2.py:453-454`, `gpu_solver.py:430`, `gto_helper.py:210`
**Проблема:** `new_pot = pot + facing_bet + raise_amount` — фишки колла
оппонента не добавлены. При facing_bet=0 прирост EV рейза при колле =
`−(1−eq)·raise_amount` < 0 при любой эквити.
**Фикс:** `new_pot = pot + raise_amount + (raise_amount - facing_bet)` —
оппонент доставляет `raise_amount − facing_bet` сверх уже уравненного.
Проверить алгебраически: при колле EV(raise) − EV(check) = `b·(2eq − 1)` —
положительно при eq>0.5. Исправить во всех четырёх солверах и `gto_helper.py`.
**Верификация:** юнит-тест: eq=0.9, facing_bet=0 → EV(bet) > EV(check);
eq=1.0 → EV(bet) строго растёт с сайзингом (до стека).

### B.2 CRITICAL — `acting_pos` post-action события: разные конвенции train/inference
**Файлы:** `generation/generate.py:883-890` (пишет «кто походил») vs
`collect.py:878-885`, `evaluate.py:626-631`, `generate_opponent.py:678-685`
(пишут «кто ходит следующим»)
**Фикс:** привести `generate.py` к конвенции **next-player** (3 из 4 call sites
уже такие): `"active_pos": table.active_player` после `step()`.
**Верификация:** интеграционный тест: одна и та же раздача, прогнанная через
generate.py-путь и collect.py-путь, даёт побайтно совпадающие event dicts
(кроме карт/рук по построению).

### B.3 CRITICAL — Модификаторы агентов: неверный нормализатор softmax

`generation/generate.py:834, 913`
**Фикс:** в `apply_modifiers` использовать тот же per-scenario нормализатор,

**Верификация:** тест: модификатор `temperature` с тем же значением, что у

**Фиксы:**
1. Глобальный dead-set при фиксации рук: исключать борд И уже зафиксированные

### B.5 MAJOR — Солвер/генерация: систематические искажения таргетов
1. **Сайзинг-конверсия** (`generate.py:272-273, 425-427`): знаменатель
   `pot` → `pot + facing_bet`, чтобы фракция солвера соответствовала
   `raise_pct * effective_pot` стола (`table.py:69`). Иначе EV-метки посчитаны
   для рейза в 2× крупнее при facing pot-bet.
2. **Фолд при бесплатном чеке** (`generate.py:423, 834-836`): при
   `facing_bet == 0` исключать fold из softmax (маскировать −inf), как это
   делает `GameState.get_legal_actions` в MCTS — устранить train/inference gap
   и источник фолд-массы (вероятный со-виновник исторических 97% фолдов).
3. **Дубли capped-бинов** (`generate.py:515-519`): бины с
   `actual_bet >= stack` схлопывать в ОДИН all-in (маскировать дубли −inf в
   softmax и не сэмплировать их), чтобы шов-масса не умножалась на k дублей.
4. **Мультивей-рейз** (`gpu_solver_v3.py:558-575, 876-880`):
   `p_fold·(pot − hero_invested)` кредитует весь пот за фолд ОДНОГО из N
   оппонентов. Фикс: primary-оппонента выбирать как агрессора/следующего
   ходящего (не seat 0), и при N>1 живых — фолд primary даёт переход к поту с
   остальными (минимум: `p_fold · EV_vs_остальных`, аппроксимация
   `p_fold · (доля пота)` недопустима). Минимально честная модель:
   `p_all_fold = Π p_fold_i` для выигрыша пота без шоудауна, иначе showdown EV
   против коллеров.
5. **`_street_discount` знак-асимметричен** (`gpu_solver_v3.py:613-614`):
   умножение отрицательного call_ev на 0.92 улучшает плохие коллы. Фикс:
   применять дисконт только к положительной части
   (`call_ev = min(call_ev, call_ev * discount)`) либо убрать дисконт.
6. **3-беты классифицируются как «open»** (`generate.py:845-848`): любой
   префлоп-рейз кроме all-in → «open» → слайс (0,1) → рейндж не сужается.
   Фикс: считать рейзы поверх рейза как `"3bet"` (по числу рейзов на улице).
7. **`geometric_factor` × отрицательный ev_on_reraise**
   (`gpu_solver_v3.py:870-872`): не применять усиление к отрицательным EV.
8. **Веса комбо в response-частотах** (`gpu_solver_v3.py:772-783`):
   p_fold/p_call/p_reraise считать взвешенно `combo_weights` (консистентно с
   эквити, которые они гейтят).
9. **EQR preflop IP** (`gpu_solver_v3.py:74-90`): префлоп позицию закрывает BB
   (seat 1), не `max(active_positions)` — поправить условие.

## Этап C. MCTS (источник value-сигнала фазы 6)

### C.1 CRITICAL — Бэкап hero-узлов: `max(W)` вместо `max(Q)`
**Файл:** `agent/mcts/mcts.py:301-308` (+ `mcts.py:276`, `re_backup_terminals`

**Проблема:** `n.W = max(c.W)` сравнивает суммы с разными N — root.Q сжимается
к 0 пропорционально концентрации визитов, при отрицательных Q выбирает
наименее посещённого ребёнка. root.Q — TD-половина value-таргета (α=0.5).
**Фикс:**
1. Hero-узлы: `n.Q = max(c.Q for c in visited)`; `n.W` вести единообразно
   суммой (`n.W += vl + leaf_value`, как у opp-узлов) — W остаётся
   бухгалтерией для re_backup-дельт, Q — статистикой решения.
2. `re_backup_terminals` (`mcts.py:626-635`): пересчёт hero-предков делать по
   новому правилу (`Q = max(child.Q)`), дельта-распространение по W оставить
   суммовым.
**Верификация:** юнит-тест: все листья возвращают одинаковое v → root.Q == v
точно (сейчас ≈0.59·v); тест с отрицательными значениями: root.Q = max(Q
детей), не зависит от распределения визитов.

**Верификация:** тест на синтетической раздаче: для opp-шагов

### C.5 MAJOR — Сайд-поты и возврат неуравненной ставки в terminal_eval

**Проблема:** короткий олл-ин кредитуется `equity × полный пот` (включая

**Фикс (в terminal_eval, движок не трогаем сверх 0.1):**
1. Кап выигрыша героя: `hero_share_pot = Σ_p min(invested_p, invested_hero)`;

**Верификация:** юнит-тесты: короткий олл-ин с eq=1.0 выигрывает ровно main
pot; непокрытая ставка возвращается (EV ставки при всех-олл-ин == 0).

## Этап D. Тренировочный пайплайн

### D.1 CRITICAL — LR-расписание фазы 6
**Файл:** `pipeline.py:755-768`, конфиг `estimated_steps_per_cycle: 70`
**Проблема:** `CosineAnnealingLR` периодичен за `T_max`: при реальном масштабе
LR начнёт расти обратно и осциллировать на поздних циклах.
**Фикс:** убрать зависимость от `estimated_steps_per_cycle`:
1. После сбора данных цикла k вычислять фактические шаги:
   `steps_k = epochs * ceil(n_examples_k * (1 - val_split) / batch_size)`.
2. Rolling-horizon: `T_max_remaining = steps_k * (n_cycles - k)`; пересоздавать
   scheduler на цикл с `last_epoch`-смещением, ИЛИ проще и надёжнее — жёсткий
   клип: при `last_epoch >= T_max` держать `eta_min` (никогда не расти).
   Реализовать клип в любом случае как страховку.
3. Warmup — только на цикле 0.
**Верификация:** лог LR за весь прогон монотонно невозрастающий после warmup.

### D.2 MAJOR — MCTS train/val split не hand-aware
**Файл:** `mcts_predict/train.py:590-600`
**Фикс:** использовать `hand_aware_split` (как во всех остальных фазах) по
`hand_id` примера — chain примера t содержит корни примеров t+1..t+5 той же
раздачи, случайный сплит = прямая утечка.
**Верификация:** assert: ни один hand_id не встречается в обоих сплитах.

### D.3 MAJOR — Teacher forcing подаёт приватный взгляд оппонента

недоступных при поиске входах; recon тянет эмбеддинги к состоянию с чужими
картами.
**Фикс:** teacher forcing применять ТОЛЬКО к hero-owned шагам
(`step.is_hero == True` и тот же агент); для opp-шагов всегда использовать
rolled latent context. Recon-лосс на opp-шагах отключить (таргет
принципиально невычислим без чужих карт).
**Верификация:** тест: при p=1.0 входы opp-шагов не содержат чужих hand-карт.
