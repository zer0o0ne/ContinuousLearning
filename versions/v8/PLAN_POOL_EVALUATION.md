# Исправленный Q-оракул и матчевый evaluation

Реализовано в v8. Evaluation работает с 2–9 игроками и читает диапазоны числа
игроков и стеков из `game.players_range` / `game.stack_bb_range`. Модель и
функция обучения не меняются. Результаты `training/warm` могут обновлять
PFSP-распределение следующей итерации, как описано ниже.

## Оракул и переход со старой разметки

`HandSpec.runout_seed` отделяет вспомогательные завершения борда от реальных
карт и действий. В `_label_plan` отдельные потоки создаются до выбора карт:
игровой, вспомогательный и поток для seed действий. Каждый внешний sample
получает новый вспомогательный seed; все его альтернативные действия разделяют
seed и кеш. Независимый повтор метки обновляет также случайность действий.
Будущие карты и остаток колоды не участвуют в seed baseline.

Для точной baseline B при фиксированных live/bets справедливо
E[B(S')|s]=B(s). При независимой вспомогательной выборке U, E_U[b(s,U)]=B(s),
поэтому E[b(S',U)-b(s,U)|s]=0. Это исправляет смещение CV, а не остальные
аппроксимации oracle (likelihood floor, subsampling диапазонов и т. п.).

Значения `oracle.samples_per_action=128` и `oracle.runout_samples=16` сохранены.
Нового переключателя «старый/исправленный баг» нет. Версия оценщика
`independent_runout_cv_v2_skip_truncated` записывается автоматически в `q_estimator` вместе
с параметрами, влияющими на метки. Температура цели и размеры батчей не являются
новой семантикой Q. Группировка работы по батчам/workers не задаёт seed.

Проверяются оба пути resume: готовый `labels.json` и частичная разметка с
`labels/play.json`. Несовместимые метки незавершённого обучения перестраиваются;
старый каталог сохраняется как `labels.stale[.N]`. Готовые исторические
чекпоинты остаются доступными и не переобучаются автоматически. Новые
чекпоинты и метрики записывают версию использованной разметки.

## Что измеряет оценщик

Он играет полные раздачи новым и предыдущим чекпоинтами. На итерации 0
референс — `agent_init`. Результат — выигрыш в BB/100, без деления на банк.

Есть два отдельных benchmark:

- `current`: все участники пула перед добавлением нового агента, равномерно,
  без повторений внутри стола — прежний равномерный эвал;
- `training`: тот же пул с вероятностями выбора соперников при сборе меток
  этой итерации. Каждый слот выбирается независимо, с повторениями, как в обучении.

`anchor` удалён. Веса `training` включают PFSP, кластеризацию и uniform floor.
Это вероятности до обновления sampler по результатам текущей итерации. Они
сохраняются в `labels.json.pool_distribution`, попадают в identity и отчёт
эвала. Для старых чекпоинтов распределение восстанавливается из sampler в
`labels.json` и настроек обучения в чекпоинте. Standalone runner использует
тот же путь. Эвал не продвигает RNG обучающего sampler.

Каждая итерация печатает имя каждого участника, вероятность занятия одного
слота, PFSP-вес, кластер и исторический результат героя против него.
Парное сравнение использует одну смесь для обоих чекпоинтов. Между итерациями
пул и его веса меняются: абсолютные значения сами по себе не задают кривую
улучшения на неизменном наборе соперников.

Один cold-блок: выбрать число игроков N, стек, N−1 соперников, колоду и
случайность; сыграть N циклических посадок каждого из двух чекпоинтов.
Итого 2N раздач. Результат блока — среднее по посадкам. Все варианты используют
общие карты и потоки случайности, но принимают собственные действия.

Один warm-блок — H раздач в каждой из этих 2N посадок. Каждая линия имеет
собственную историю и адаптацию. Внутри линии позиции ротируются между руками,
а соответствие постоянным слотам сохраняется. Герой использует embedding-сеть
своего поколения и её настройки K/R/fit_lr/fit_reg; игроки из пула — свои сети
и существующий режим `embedding_net.pool_agent_vectors`. В холодном блоке
истории нет. Во время evaluation sampler остаётся фиксированным. После
завершения всех режимов внешний обучающий цикл может обновить его для
следующей итерации; loss и выбор чекпоинтов не используют результаты эвала.

По умолчанию дополнительно применяется исправленная card/fold-CV с M=16.
Полных oracle rollout на каждом действии и нового value-head здесь нет.
Сохраняются и обычный выигрыш (`raw`), и скорректированный (`cv`). Запросы
одной нейросети из разных столов батчатся с собственными embedding-таблицами.

## Статистика и точность

Для B независимых блоков D_b = Z_new,b − Z_old,b:

```
delta_bb100 = 100 * mean(D)
SE_delta_bb100 = 100 * sample_std(D) / sqrt(B)
```

В warm независимая единица — целая сессия со всеми посадками, а не рука.
При разных N блоки получают равный вес, сохраняя равномерную смесь столов;
усреднение всех физических рук дало бы лишний вес большим столам.

Отчёт включает absolute new/old, paired delta, SD единицы, SE, приблизительный
нормальный доверительный интервал, число единиц, число реально сыгранных рук
и время. Для одной единицы SD/SE/интервал отсутствуют. Малое число сессий может
давать ненадёжное нормальное приближение; начальный бюджет является пилотом.

Также записывается оценка размера **нового независимого** запуска для заданной
полуширины интервала: ceil((z * 100 * SD / h)^2), минимум две единицы. Это
планирование по пилоту, а не гарантия точности. Автоматической остановки по
первому положительному интервалу нет; запускается фиксированный бюджет.

Разбивки: по числу игроков и по сопернику. В multiway результат «по сопернику»
означает выигрыш героя на столах, где этот соперник присутствовал. Эти группы
перекрываются и не являются аддитивным разложением выигрыша.

Старая `ev_agent` сохранена для диагностики, явно обозначена как dimensionless
normalised Q; она не заменяет матчевый BB/100.

## Обновление PFSP по evaluation

В основном конфиге `pool_sampling.evaluation_weight = 0.5`. При отсутствии
ключа или значении `0` сохраняется прежний PFSP только по раздачам сбора меток.
Допустимый диапазон — `[0, 1]`.

Внешний цикл принимает только `training/warm`, текущего кандидата `new` и его
абсолютный результат против каждого участника. Дельта `new − old`, кандидат
`old`, cold и равномерный `current` не участвуют. Берётся `cv`, если он считался,
иначе `raw`. В multiway это результат на столах с данным соперником; его
повторное присутствие за одним столом не умножает число наблюдений.

Каждая независимая warm-сессия уже усреднена по рукам и циклическим посадкам
текущего агента. Сессии получают равные веса. Для каждого соперника среднее
`r` по пригодным сессиям текущей итерации добавляется как **одно** наблюдение
в отдельный накопитель, независимо от числа физических раздач или бюджета
эвала. Увеличение бюджета повышает точность `r`, а не его вес относительно
предыдущих итераций и разметки.

Перед добавлением нового наблюдения накопители `S` (сумма BB/100) и `M`
(масса наблюдений) умножаются на существующий `result_decay` (в конфиге `0.8`).
Затем для встретившегося соперника `S += r`, `M += 1`, и оценка эвала — `S/M`.
Среднее сбора меток продолжает храниться отдельно как сумма BB / число рук.
При наличии обоих источников PFSP ранжирует их смесь:

```
w = evaluation_weight * min(1, M)
score = (1 - w) * collection_bb100 + w * evaluation_bb100
```

Так при свежих оценках доля эвала равна `0.5`; если соперник долго не
появляется в warm-эвале, его доля постепенно уменьшается. Если по сопернику
есть только эвал, используется его результат; если данных нет в обоих
источниках, остаётся прежняя максимальная hardness. Полностью отброшенные
сессии не создают нулевых результатов. Отсутствующий `training/warm` не
заменяется другим режимом.

Обновление идёт после всех измерений, перед фиксацией завершённой итерации.
`state.json` атомарно сохраняет sampler, номер последней учтённой итерации и
`evaluation_feedback` с источником, оценщиком, числом сессий и результатами по
соперникам. Повторный учёт той же или более старой итерации запрещён. После
сбоя до сохранения загружается прежний sampler и уже сыгранные блоки эвала;
обновление вычисляется заново и фиксируется один раз. Старые состояния без
этих полей загружаются с пустой статистикой эвала. Завершённые итерации
автоматически не пересчитываются.

`pool_eval_pipeline.py` по-прежнему только измеряет: даже при включённом
`evaluation_weight` standalone-запуск не изменяет обучающий sampler.
В логах есть отдельная строка о применении feedback; строки весов следующей
итерации показывают сглаженный `eval` и фактическую долю `eval_mix`.

## Раздачи, достигшие лимита действий

Лимит `6 * N + 8` сохраняется как защита от затянувшейся игры. Его достижение
не прерывает обучение или pool evaluation. Недоигранная раздача исключается
из PFSP-результатов, обучения embeddings, истории warm-fit и oracle-разметки.
В oracle, если хотя бы одно действие общего sample упёрлось в лимит, весь этот
sample исключается из усреднения всех действий. Метка без оставшихся samples
пропускается. Если весь корпус или набор меток пуст, соответствующее обучение
пропускается, текущие веса сохраняются, цикл продолжается.

В эвале исключается этот номер руки у обоих кандидатов во всех посадках данного
блока; остальные руки warm-сессии продолжаются. Индексы рук и ротация мест
сохраняются. Полностью отброшенный блок сохраняется на диск и при resume не
переигрывается бесконечно. Отчёт содержит `attempted_hands`, `truncated_hands`
(реально достигшие лимита), `discarded_hands` (с учётом парных исключений),
`hands` и число пригодных статистических единиц. При отсутствии пригодных рук
оценка — `null`, а не ноль. Числа пропусков печатаются в логи.

Результаты после исключений относятся к оставшимся раздачам; исключение по
длине траектории может менять измеряемое распределение. Поэтому счётчики
пропусков сохраняются рядом с оценкой, а недоигранный результат не заменяется нулём.

## Новые ключи config.json: pool_evaluation

| Ключ | Значение в основном конфиге | Назначение |
|---|---|---|
| `enabled` | `true` | Выполнять этап после обучения и oracle-gap каждой новой итерации. При отсутствии секции этап выключен. |
| `run` | `"weighted_v1"` | Новый каталог и пространство seeds для взвешенного эвала и пропуска недоигранных рук. Старые результаты сохраняются отдельно. |
| `benchmarks` | `["current", "training"]` | Какие смеси измерять; бюджеты ниже задаются **на каждый benchmark**. |
| `cold_blocks` | `128000` | Независимые cold-блоки; `0` отключает cold. Каждый стоит 2N раздач. |
| `warm_sessions` | `160` | Независимые warm-сессии; `0` отключает warm. Каждая стоит 2NH раздач. |
| `warm_hands_per_session` | `100` | H: длина каждой линии адаптации, включая её прогрев. |
| `blocks_per_batch` | `512` | Сколько независимых единиц играть вместе для батчирования сетей. Влияет на память и максимальную потерю работы при сбое. |
| `batch_hands` | `2048` | Предел одновременно играемых рук внутри driver. |
| `control_variate` | `true` | Считать исправленный CV-выигрыш вместе с raw; отключение оставляет raw. |
| `runout_samples` | `16` | M вспомогательных бордов для CV; число обычных раздач не увеличивает. |
| `fit_window` | `500` | Сколько последних рук своей линии герой использует для warm-fit. |
| `confidence` | `0.95` | Уровень приблизительного нормального интервала. |
| `target_halfwidth_bb100` | `10.0` | Желаемая полуширина для расчёта размера следующего независимого замера. Бюджет текущего запуска не меняет. |
| `seed` | `1729` | Seed оценки; пространства итераций, benchmark, режима, run и блока разделены. |

Для фиксированного числа игроков N общее число раздач равно
`len(benchmarks) * 2 * N * (cold_blocks + warm_sessions * warm_hands_per_session)`.
С текущими значениями на двух benchmark суммарно будет:

| Режим столов | Попыток раздач до исключений |
|---|---:|
| 2 игрока | 1 152 000 |
| 6 игроков | 3 456 000 |
| 9 игроков | 5 184 000 |
| Равномерно 2–9 | в среднем 3 168 000 |

В основном конфиге задано 128000 холодных блоков и 160 тёплых сессий на
benchmark. При длине warm-сессии 100 рук в HU это 1 024 000 холодных раздач
и 128 000 тёплых раздач суммарно по двум benchmark.

В HU полный холодный пакет теперь подаёт `512 * 2 * 2 = 2048` раздач.
При R=25 у обоих кандидатов и игроков пула тёплый пакет из 160 сессий подаёт
`160 * 2 * 2 * 25 = 16000` раздач между обновлениями представлений; драйвер
держит одновременно не больше 2048. Benchmark выполняются отдельно.
Количество рук в работе не равно размеру запроса одной сети: решения
группируются по участнику пула. Скорость на целевом GPU требует замера.

Если указанная скорость не включает CV и fit, они добавят время. Фактические
`play_seconds`, `hands_per_second`, `invocation_seconds` и время этапа в
`metrics.json` записываются автоматически. Издержки fingerprints входят во
время вызова, а `hands_per_second` относится к игре и fit.

Снижение `agent_train.heldout_fraction` само по себе не экономит Q-разметку:
разбиение по-прежнему выполняется после oracle. Перенос этого бюджета на
матчи не включён: диагностический holdout сохраняется.

## Запуск и сохранение

Обычный `pipeline.py --config config.json` включает этап автоматически.
Число игроков и стеки меняются в общей секции `game`, никаких HU-констант в
pool evaluation нет. Для равномерного 9-max выбранный пул должен содержать
хотя бы 8 различных соперников. В `training` разрешены повторения.

После сбоя на action cap достаточно перезапустить pipeline с обновлённым
config.json. Уже сохранённый агент и метки будут загружены; эвал начнётся в
новом `weighted_v1`. Если используется отдельная копия конфига, замените
`anchor` на `training` и задайте новое имя `pool_evaluation.run`.

Для сохранённых чекпоинтов, из `versions/v8`:

```bash
python pool_eval_pipeline.py --config config.json --iteration 7 --reference-iteration 3 --run compare_7_3
```

Без `--reference-iteration` сравнивается с предыдущей итерацией. `-1` означает
`agent_init`. Загружаются веса и поколения embedding из того же experiment;
обучения и сбора лейблов этот runner не запускает.

Выход: `data/v8/<experiment>/iter_XXXX/pool_evaluation/<run>/report.json`,
`identity.json` и JSON по каждому завершённому независимому блоку. Запись
атомарная; после сбоя завершённые единицы переиспользуются, незавершённые
переигрываются. После смены весов, параметров игры, смеси или бюджета старый
run не дополняется: нужно новое имя. Смена размеров батчей разрешена;
GPU-округление в батчах может менять отдельные пограничные случайные действия.

Идентичность включает содержимое весов, параметры процедурных соперников,
их таблицы и стили, поколения embedding, конфиг и версию оценщика. Отдельная
проверка идентичности добавлена и в Slumbot-runner: старые JSONL без идентичности
нельзя незаметно дописывать новым чекпоинтом; для нового запуска требуется
новое `evaluation.run`. Завершённые исторические результаты сохраняются.

## Проверка

CPU-тесты проверяют точное ожидание по всем реальным риверам и конечной
вспомогательной выборке для 2/3/9 игроков, включая side pots; раздельные RNG и
кеш, последовательный/параллельный сбор, resume, все посадки, статистическую
единицу, историю адаптации и неизменность обучаемых весов/состояния sampler
при включении evaluation. GPU throughput и фактическая дисперсия текущего
чекпоинта измеряются отдельным запуском на машине обучения.

Полный прогон 17.09.2026: `python -m pytest tests/ -q --disable-warnings` —
658 passed, 7 warnings, 174.38 с; GPU не использовался. Параллельные тесты
запускались вне filesystem-песочницы из-за ограничений на torch_shm_manager.

Проверка 23.09.2026 после замены anchor и обработки action cap: полный набор —
667 passed, 7 warnings, 173.93 с; отдельно прошёл добавленный тест восстановления
весов из старого `labels.json` без snapshot распределения. Проверены пустой
обучающий корпус, пустые oracle-метки, парное исключение рук в cold/warm,
resume полностью отброшенных блоков, PFSP + dedup + floor и неизменность
обучения при включении эвала. Полный набор запускался вне песочницы для
работы `torch_shm_manager`; GPU не использовался.

После подключения `training/warm` к PFSP: **677 passed, 7 warnings, 174.87 с**
на CPU. Проверены выбор только текущего кандидата и нужного режима, равный
вес независимых сессий, независимость доли эвала от бюджета, сглаживание,
старые состояния, рост пула, пустые результаты и сбой перед атомарной записью.
Повторный запуск после такого сбоя дал то же состояние sampler, что и
непрерывный прогон; standalone-эвал не изменил обучающий state.
